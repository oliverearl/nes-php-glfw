# Contributing

Thanks for taking an interest in this NES emulator. This project is a technical demonstration of NES hardware emulation in PHP, so contributions are most useful when they keep accuracy, readability, and testability in view.

## Before You Start

- Read [README.md](README.md) for setup, usage, available commands, architecture, and project status.
- Read [AGENTS.md](AGENTS.md) for coding standards, testing expectations, and emulator-specific guidance.
- Check the existing issues before opening a new report or feature request.
- Do not commit or attach copyrighted commercial ROMs. Use homebrew ROMs, synthetic fixtures, or public test ROMs with compatible licenses.

## Local Setup

Use PHP 8.5+ with PHP-GLFW enabled in the CLI and install the locked dependencies with `composer install`. Follow the
[installation guide](README.md#installation) before running Composer. Use the same interpreter for Composer, PHPUnit, and the application.
Python 3.10+ is required only for the benchmark supervisor and its tests. Graphical smoke tests require a desktop display and OpenGL context.

## Development Workflow

1. Create a focused branch for the change.
2. Add or update tests before changing behavior where practical.
3. Keep changes scoped to one bug fix, feature, or cleanup.
4. Update documentation when behavior, workflow, controls, architecture, or contributor expectations change.
5. When changing agentic development guidance, update [AGENTS.md](AGENTS.md) first, then keep Cursor, Claude, Copilot, Junie, and contributor-facing docs in sync.
6. Run `composer test` and `composer quality:check` before opening a pull request. Run
   `python3 -m unittest discover -s tests/BenchmarkTools -v` when changing the Python tools.
7. For frontend changes, smoke-test startup, keyboard controls, and ROM loading on a real display. CI exercises the headless paths.

## Tests

New public behavior should include tests following the structure in [AGENTS.md](AGENTS.md).

When adding ROM-based tests, prefer synthetic ROMs generated by test helpers or redistributable homebrew/test ROMs. Document the source, upstream revision, license, and any transformations for committed third-party fixtures in [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md) or an adjacent provenance file.
Do not copy generated captures or local game ROMs into the repository. Missing optional ROM fixtures are skipped, so check the skip summary rather than treating every green run as full compatibility validation.

For performance investigations, see the optional [profiling and benchmarking tools](tools/README.md). Optimisations should preserve emulated work and output checksums. Accuracy fixes may intentionally change them; explain the independent evidence and refresh the baseline after validation.

The CPU's pinned SingleStepTests sample compares instruction state, listed memory, and cycle totals. It does not yet verify every bus access or its ordering; see [the fixture guide](tests/Support/Cpu/SingleStepTests/README.md).

## Maintainer Release Checklist

Before tagging a release:

- Update the upcoming section of [CHANGELOG.md](CHANGELOG.md), check its version/date, and reconcile README compatibility limits with the final code.
- Verify third-party fixture provenance and licenses; exclude local ROMs, captures, caches, and credentials from the release.
- Install from the committed lock file in a clean checkout, then run `composer validate`, `composer audit --locked --abandoned=report`, `composer test`, `composer quality:check`, and the Python tool tests. Investigate warnings and skipped tests. Composer currently warns about the intentional VISU commit pin; review that constraint when upgrading the framework.
- On a native display, smoke-test no-ROM startup, initial ROM loading, drag/drop and repeated loading, keyboard controls, normal pacing, `--drop-frames`, and `--profile`. Headless CI cannot verify the window or input devices.
- Confirm the final commit's CI checks are green, tag that commit, and review the tag's CI results before publishing release notes. Publishing is a maintainer action; these checks do not publish automatically.

## Pull Requests

Pull requests should include:

- A short summary of the change.
- The tests or checks that were run.
- Screenshots, profiler output, or benchmark results when the change affects rendering, controls, timing, or performance.
- Documentation updates when contributor workflow or emulator behavior changes.

For AI-assisted changes, mention the tool or agent in the pull request body and review generated code carefully before submitting.
